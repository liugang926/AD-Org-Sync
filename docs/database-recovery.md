# Django 数据库恢复操作说明

适用于新版本的 `django.sqlite3`，不适用于旧平台 `app.db`。数据库恢复会改变应用记录，须由管理员明确授权；下列步骤是运维说明，编写文档不代表已在宿主执行。

1. 记录当前镜像完整 SHA、Compose 文件、配置引用和所需迁移版本。先停止系统同步入队，再停止 Web 与 worker，避免旧任务继续写 AD。保留现场数据库及 WAL/SHM 文件，不覆盖唯一副本。
2. 将选定备份复制到隔离数据目录，使用与该备份对应的已验证 Django 镜像运行 `python -m sync_app.cli db_check`。保留原受限凭据与 CA；不要将凭据写进报告。不要用旧 2.x 镜像打开新数据库。
3. 若备份与目标应用的迁移不同，先在副本上测试迁移和 `db_check`。不假定镜像回退能逆转数据库结构。校验失败时保留现场，不继续覆盖运行数据。
4. 在隔离副本中暂时关闭定时同步与员工重置，清理员工验证会话及管理员会话；将旧排队、运行任务标记失败。恢复的数据可能含已使用的验证会话和过时计划，不能直接重放。
5. 核对配置、来源身份锚点、人员及部门绑定数量。使用实时 AD 只读查询确认 GUID、保护状态和受管 OU；已有绑定指向的对象不存在或被替换时转人工处理。数据库恢复不会恢复 AD 属性、密码、账号状态或目录结构。
6. 副本检查通过且管理员确认替换后，在服务停止状态下替换数据库，并确保所属用户及权限正确。保留恢复前副本。先启动 Web 验证管理员登录和数据库，再启动 worker，确认中断任务没有重放。
7. 重新生成同步预览，审查与真实目录的差异，再按明确授权执行。最后恢复系统调度和员工服务，并核验外部 HTTPS、`/healthz`、`/readyz` 与当前镜像 SHA。
